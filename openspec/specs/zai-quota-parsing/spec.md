# zai-quota-parsing Specification

## Purpose
Разбор ответов о квоте провайдеров (z.ai и Anthropic) в окна пятичасового и недельного
лимита, распознавание отказов и поведение опроса после отказа.
## Requirements
### Requirement: Окна квоты определяются поэлементно, без переключателя версии формата
Расширение ДОЛЖНО (SHALL) классифицировать каждую запись `data.limits[]` самостоятельно,
разрешая период окна по паре `(type, unit)` там, где он указан, и откатываясь к позиции
в массиве только для записей, где он не указан. Расширение НЕ ДОЛЖНО разветвлять разбор
всего ответа по одной обнаруженной версии формата.

Окнами квоты считаются записи с `type`, равным `TOKENS_LIMIT` или `CREDIT_LIMIT`. Коды
единиц периода: `3` — часы, `5` — месяцы, `6` — недели; любой другой код считается
неразрешённым, а не угадывается. Часовой период означает пятичасовое окно независимо от
`number`; если часовых окон несколько, берётся первое.

Окно квоты с периодом, отличным от часов и недель, классифицируется как прочее: оно
не занимает ни пятичасовой, ни недельный слот и не участвует в позиционном распределении.

#### Scenario: Токенный ответ нового тарифа разбирается по единице периода
- **WHEN** ответ содержит `TOKENS_LIMIT` с `unit: 3, number: 5` и `TOKENS_LIMIT`
  с `unit: 6, number: 1`
- **THEN** первое становится пятичасовым окном, второе — недельным

#### Scenario: Смешанный ответ разрешается поэлементно
- **WHEN** одно окно квоты несёт `unit: 3`, а другое не несёт `unit` вовсе
- **THEN** первое классифицируется по единице периода, второе — по позиции в массиве

#### Scenario: Недокументированный код единицы не угадывается
- **WHEN** окно квоты несёт `unit: 2`
- **THEN** запись считается неразрешённой и классифицируется по позиции, а не как сутки

#### Scenario: Окно с месячным периодом не занимает слот
- **WHEN** окно квоты с `unit: 5` соседствует с часовым и недельным окнами
- **THEN** пятичасовое и недельное окна берутся из часовой и недельной записей,
  а месячная игнорируется

### Requirement: Кредитные тарифы читаются как окна квоты
Расширение ДОЛЖНО (SHALL) считать записи `CREDIT_LIMIT` окнами квоты наравне с записями
`TOKENS_LIMIT`, чтобы кредитные тарифы сообщали утилизацию, а не ноль.

#### Scenario: Кредитный тариф сообщает утилизацию
- **WHEN** ответ содержит только записи `CREDIT_LIMIT` для пятичасового и недельного окон
- **THEN** оба окна сообщают свою утилизацию, а недельное окно считается имеющимся

#### Scenario: У кредитного тарифа нет записи MCP
- **WHEN** кредитный ответ не содержит `TIME_LIMIT` вовсе
- **THEN** разбор проходит успешно и ни одно окно квоты не выводится из отсутствующего
  лимита MCP

### Requirement: Лимит MCP никогда не принимается за окно квоты
Расширение ДОЛЖНО (SHALL) исключать записи `TIME_LIMIT` из отбора пятичасового и недельного
окон независимо от их позиции в массиве и сообщённого процента.

#### Scenario: Исчерпанный лимит MCP не поднимает предупреждение о квоте
- **WHEN** запись `TIME_LIMIT` на 99 % предшествует двум окнам квоты с низкой утилизацией
- **THEN** сообщённые пятичасовая и недельная утилизации берутся из окон квоты, а статус
  лимита не становится предупреждением

### Requirement: Позиция определяет окна при неразрешённом периоде, а время сброса лишь накладывает вето
Для каждого окна квоты с неразрешённым периодом расширение ДОЛЖНО (SHALL) определять окно
по позиции среди окон квоты, считая первого кандидата, не отвергнутого как заведомо
далёкий, пятичасовым окном, а следующее оставшееся окно квоты — недельным.

Окно квоты исключается из пятичасового слота, только если его `nextResetTime` отстоит
больше чем на шесть часов. Отсутствие `nextResetTime` не исключает кандидата. Время сброса
не используется для положительного выбора окна. Если исключены все кандидаты, расширение
возвращается к порядку массива, а не оставляет пятичасовое окно неназначенным.

Если окон квоты больше двух, используются только первые два; каждое следующее игнорируется,
а не замещает недельное окно.

#### Scenario: Устаревший ответ разбирается по порядку
- **WHEN** две записи `TOKENS_LIMIT` не несут ни `unit`, ни `number`
- **THEN** первая становится пятичасовым окном, вторая — недельным

#### Scenario: Недельное окно, сбрасывающееся раньше, сохраняет свою позицию
- **WHEN** первое окно квоты сбрасывается через два часа, а второе, на 100 %, — через
  восемьдесят минут
- **THEN** первое остаётся пятичасовым окном, второе — недельным

#### Scenario: Далёкий первый кандидат отвергается по вето
- **WHEN** первое окно квоты сбрасывается через трое суток, а второе — через час
- **THEN** второе становится пятичасовым окном, первое — недельным

#### Scenario: Простаивающие окна сохраняют порядок массива
- **WHEN** ни одно окно квоты не несёт `nextResetTime`
- **THEN** решает порядок массива, и первое становится пятичасовым окном

#### Scenario: Единственное окно квоты означает отсутствие недельного
- **WHEN** ответ содержит ровно одно окно квоты
- **THEN** недельное окно считается отсутствующим с нулевой утилизацией

#### Scenario: Отвергнутые все кандидаты возвращают разбор к порядку массива
- **WHEN** оба окна квоты сообщают `nextResetTime` дальше шести часов
- **THEN** первое становится пятичасовым окном, второе — недельным

#### Scenario: Третье окно квоты игнорируется
- **WHEN** три окна квоты не несут разрешимого периода
- **THEN** первые два заполняют пятичасовое и недельное окна, третье игнорируется

### Requirement: Утилизация предпочитает абсолютные величины, когда они сходятся с процентом
Расширение ДОЛЖНО (SHALL) выводить утилизацию из `currentValue / usage` там, где окно квоты
сообщает и `currentValue`, и положительный `usage`, — но только если это значение сходится
с сообщённым `percentage` в пределах 1,5 процентного пункта. Иначе используется
`percentage`.

Если `percentage` отсутствует или не является числом, а величины пригодны, используется
выведенное отношение без сверки. Если непригодны ни `percentage`, ни величины, утилизация
равна нулю. Утилизация ограничивается диапазоном от 0 до 1.

`usage` — это лимит, а `currentValue` — израсходованное; расширение не трактует эти имена
наоборот.

#### Scenario: Выведенное отношение уточняет целочисленный процент
- **WHEN** окно квоты сообщает `currentValue: 16693`, `usage: 28000` и `percentage: 59`
- **THEN** сообщённая утилизация составляет около 0,596, а не 0,59

#### Scenario: Расхождение возвращает разбор к сообщённому проценту
- **WHEN** выведенное отношение отличается от `percentage` больше чем на 1,5 процентного
  пункта
- **THEN** сообщённая утилизация берётся из `percentage`

#### Scenario: Процент больше 100 ограничивается
- **WHEN** окно квоты сообщает `percentage: 250`
- **THEN** сообщённая утилизация равна 1

#### Scenario: Величины без процента используются напрямую
- **WHEN** окно квоты сообщает `currentValue: 16693` и `usage: 28000`, но не `percentage`
- **THEN** сообщённая утилизация составляет около 0,596, а не ноль

### Requirement: Окно без пригодного времени сброса сообщает горизонт полного окна
Расширение ДОЛЖНО (SHALL) сообщать секунды до сброса окна из `nextResetTime`, трактуя его
как эпоху в миллисекундах. Если `nextResetTime` отсутствует, уже в прошлом или отстоит
больше чем на 400 суток, расширение сообщает собственную длину окна: произведение `unit`
на `number`, где оно разрешается, иначе пять часов для пятичасового окна и семь суток для
недельного. Расширение не сообщает ноль для существующего окна.

#### Scenario: Простаивающее пятичасовое окно сообщает пять часов
- **WHEN** пятичасовое окно квоты не несёт `nextResetTime`
- **THEN** сообщённое время до сброса составляет около пяти часов

#### Scenario: Время сброса в прошлом откатывается к длине окна
- **WHEN** `nextResetTime` отстоит на минуту в прошлое
- **THEN** сообщённое время до сброса равно собственной длине окна

#### Scenario: Заведомо далёкое время сброса игнорируется
- **WHEN** `nextResetTime` отстоит на 500 суток вперёд
- **THEN** сообщённое время до сброса равно собственной длине окна

#### Scenario: Недельный откат равен неделе, а не суткам
- **WHEN** недельное окно квоты несёт `unit: 6, number: 1` и не несёт `nextResetTime`
- **THEN** сообщённое время до сброса составляет около семи суток

### Requirement: Величины кредитов и уровень тарифа отдаются, когда они есть
Расширение ДОЛЖНО (SHALL) отдавать необязательными данными модель тарификации, уровень
тарифа из `level`, а также израсходованную, полную и остаточную величины для каждого окна,
которое их сообщает. Модель тарификации считается кредитной, если присутствует хотя бы одна
запись `CREDIT_LIMIT`, и токенной в противном случае. Расширение не пересчитывает
`remaining`, которое вышестоящий API округляет.

Эти поля отсутствуют для провайдеров, отличных от z.ai, и для ответов, не сообщающих
абсолютных величин. Если окно сообщает израсходованное и полное, но не `remaining`,
расширение всё равно отдаёт те две величины, что у него есть, а не отбрасывает все три.

Уровень тарифа принимается только как короткая строка и отвергается — вместе со всей
записью кэша, — если он другого типа или длиннее допустимого, поскольку приходит
из внешнего API и попадает на диск прежде, чем будет отрисован.

#### Scenario: Кредитный тариф отдаёт величины и уровень
- **WHEN** окно `CREDIT_LIMIT` сообщает `currentValue: 16693`, `usage: 28000`
  и `remaining: 11306`, а ответ сообщает `level: "max"`
- **THEN** эти три величины отдаются без изменений вместе с уровнем тарифа и кредитной
  моделью тарификации

#### Scenario: Токенный тариф не отдаёт величин
- **WHEN** ответ содержит только записи `TOKENS_LIMIT`, сообщающие процент
- **THEN** величины кредитов не отдаются, а модель тарификации считается токенной

#### Scenario: Величины кредитов переживают круговой прогон через кэш
- **WHEN** данные квоты с величинами кредитов и уровнем тарифа записаны в кэш и прочитаны
  обратно
- **THEN** восстановленные данные несут те же величины и тот же уровень

#### Scenario: Окно без остатка всё равно отдаёт остальное
- **WHEN** окно квоты сообщает `currentValue` и `usage`, но не `remaining`
- **THEN** израсходованная и полная величины отдаются, а остаточная отсутствует

#### Scenario: Слишком длинный уровень тарифа обесценивает запись кэша
- **WHEN** файл кэша несёт уровень тарифа, не являющийся короткой строкой
- **THEN** вся запись отвергается, и квота запрашивается заново

### Requirement: Отказы аутентификации, приходящие с HTTP 200, распознаются
Расширение ДОЛЖНО (SHALL) считать явный `success: false` в конверте ответа признаком
неудачного запроса и не разбирать такой ответ как данные квоты, поскольку z.ai отвечает
на отвергнутый токен кодом HTTP 200, а не ошибочным статусом. Ответ, где поле `success`
опущено, разбирается обычным образом.

Расширение сопоставляет `code` конверта с классом отказа — 401, 403 и 429 как есть, 1000
и 1001 как отказ аутентификации, любой другой код как ошибку вышестоящей системы — и не
показывает `msg`, язык которого не следует запрошенной локали.

#### Scenario: Отвергнутый токен не сообщает нулевого расхода
- **WHEN** эндпоинт возвращает HTTP 200 с `{"code": 1000, "success": false}` для каждого
  способа авторизации
- **THEN** запрос квоты завершается неудачей, и расширение показывает кэш, протухшие данные
  или режим только затрат, а не 0 % использовано

#### Scenario: Успешный конверт без поля success разбирается
- **WHEN** ответ не содержит `success`, но содержит пригодные окна квоты
- **THEN** квота разбирается обычным образом

### Requirement: Повтор авторизации управляется классом отказа
Расширение ДОЛЖНО (SHALL) пробовать сначала форму с токеном-носителем, затем форму
с сырым токеном, повторяя попытку только тогда, когда первая завершилась отказом
аутентификации — пришёл ли он HTTP-статусом или конвертом ответа. При отказе любого другого
класса повтор не выполняется.

#### Scenario: Отказ аутентификации в конверте запускает повтор с сырым токеном
- **WHEN** попытка с токеном-носителем возвращает HTTP 200 и конверт с кодом 1001,
  а попытка с сырым токеном проходит успешно
- **THEN** сообщается квота из второй попытки

#### Scenario: Отказ, не связанный с аутентификацией, не повторяется
- **WHEN** первая попытка возвращает ошибку вышестоящей системы, не связанную
  с аутентификацией
- **THEN** вторая попытка не выполняется, и запрос завершается неудачей

#### Scenario: Класс определяется последним отказом
- **WHEN** попытка с токеном-носителем завершается отказом аутентификации, а попытка
  с сырым токеном — по другой причине
- **THEN** запрос завершается неудачей по этой другой причине и не записывается как отказ
  аутентификации

### Requirement: Успешный ответ без пригодных лимитов считается ошибкой
Расширение ДОЛЖНО (SHALL) считать успешный конверт, не содержащий ни `TOKENS_LIMIT`,
ни `CREDIT_LIMIT`, неудачным запросом, чтобы неизвестная форма ответа проявлялась как
протухшие или закэшированные данные, а не как нулевой расход. Тело ответа, не являющееся
корректным JSON, точно так же делает запрос неудачным.

#### Scenario: Ответ с одной лишь записью MCP завершается неудачей
- **WHEN** успешный ответ содержит только запись `TIME_LIMIT`
- **THEN** запрос квоты завершается неудачей, а не сообщает 0 % использовано

#### Scenario: Тело, не являющееся JSON, делает запрос неудачным
- **WHEN** тело ответа не разбирается как JSON
- **THEN** запрос квоты завершается неудачей без необработанного исключения

### Requirement: Разбор квоты никогда не бросает исключений
Разбор ответа о квоте ДОЛЖЕН (SHALL) всегда возвращать результат и не бросать исключений
ни при каком входе, включая null, значения, не являющиеся объектами, `limits`, не являющийся
массивом, и элементы массива, равные null или не являющиеся объектами. Неразбираемый вход
даёт нулевую утилизацию и отсутствие недельного окна.

#### Scenario: Враждебный вход даёт нули
- **WHEN** парсер получает null, строку, число, `limits`, не являющийся массивом, или массив
  с элементами null и не-объектами
- **THEN** он возвращает нулевую утилизацию без недельного окна и не бросает исключения

### Requirement: Частые повторы при отказе аутентификации не идут в API
Расширение ДОЛЖНО (SHALL) запоминать отказ класса «аутентификация» или «формат» вместе
со временем его наступления и не отправлять следующий запрос квоты автоматически (по таймеру
или по изменению файлов истории), пока с этого момента не пройдёт большее из времени жизни
кэша и пяти минут либо пока пауза не снята успешными данными. Неудачи повторяемых классов —
сетевые и сбои сервера провайдера — повторяются автоматически не чаще раза в пять минут,
независимо от времени жизни кэша и наличия кэша.

Без этого отвергнутый ключ не создаёт записи кэша, планировщик опроса считает отсутствие
кэша поводом обратиться к API, и расширение шлёт запрос на каждом тике таймера всё время,
пока ключ остаётся отвергнутым.

#### Scenario: Отвергнутый ключ не перезапрашивается каждый тик
- **WHEN** запрос квоты завершился отказом аутентификации, и автоматическое обновление
  наступает до истечения времени жизни кэша
- **THEN** запрос провайдеру не отправляется

#### Scenario: Малое время жизни кэша не укорачивает паузу
- **WHEN** время жизни кэша настроено на 60 секунд, запрос квоты завершился отказом
  аутентификации, и с тех пор прошло меньше пяти минут
- **THEN** автоматическое обновление запрос провайдеру не отправляет

#### Scenario: Подавление прекращается
- **WHEN** с момента записанного отказа аутентификации прошло большее из времени жизни кэша
  и пяти минут
- **THEN** ближайшее обновление, которое по правилам свежести кэша обращается к API,
  отправляет запрос

#### Scenario: Сетевой отказ повторяется не чаще раза в пять минут
- **WHEN** запрос квоты завершился по сетевой причине или сбою сервера провайдера, кэша нет,
  и автоматическое обновление наступает раньше чем через пять минут после неудачи
- **THEN** запрос провайдеру не отправляется

#### Scenario: Сетевой отказ не ждёт времени жизни кэша
- **WHEN** запрос квоты завершился по сетевой причине, время жизни кэша больше пяти минут,
  и с момента неудачи прошло пять минут
- **THEN** ближайшее обновление, которое по правилам свежести кэша обращается к API,
  отправляет запрос, не дожидаясь истечения времени жизни кэша

### Requirement: Отвергнутый ключ отличим от недоступности сервиса
Расширение ДОЛЖНО (SHALL) показывать отказ класса «аутентификация» отдельным состоянием,
называющим причиной учётные данные, отдельно от показа протухших или недоступных данных,
чтобы отказ, требующий действий пользователя, не выглядел так же, как отказ, который
пройдёт сам. Состояние невыполненного входа ДОЛЖНО (SHALL) показываться только тогда,
когда учётных данных нет.

#### Scenario: Отвергнутый ключ называется отвергнутым
- **WHEN** провайдер отвергает настроенный токен
- **THEN** расширение сообщает, что учётные данные отвергнуты

#### Scenario: Временная недоступность не выдаётся за проблему с ключом
- **WHEN** запрос квоты завершился по сетевой причине или сбою сервера провайдера
- **THEN** расширение показывает закэшированные или протухшие данные, а без кэша — режим
  затрат или отсутствие данных, не называя учётные данные и не сообщая, что вход
  не выполнен

#### Scenario: Провайдер без входа не называется невыполненным входом
- **WHEN** провайдер — Bedrock, API-ключ или сторонний адрес, либо запросы к API выключены
  пользователем, и нет ни кэша, ни локальных затрат
- **THEN** показывается отсутствие данных, а не «вход не выполнен»

#### Scenario: Отсутствие учётных данных называется невыполненным входом
- **WHEN** учётных данных провайдера нет, кэша нет, и локальных затрат нет
- **THEN** расширение сообщает, что вход не выполнен

### Requirement: Полностью исчерпанное окно сообщает статус denied
Расширение ДОЛЖНО (SHALL) сообщать статус лимита как `denied`, когда пятичасовая или
недельная утилизация достигает 1, чтобы исчерпанная квота отличалась от приближающейся
к исчерпанию.

#### Scenario: Исчерпанное недельное окно даёт denied
- **WHEN** недельное окно сообщает 100 % расхода
- **THEN** статус лимита равен `denied`, а не предупреждению

#### Scenario: Высокая, но не исчерпанная утилизация остаётся предупреждением
- **WHEN** наибольшее окно сообщает 90 % расхода
- **THEN** статус лимита равен предупреждению

### Requirement: Число рассматриваемых записей лимитов ограничено
Расширение ДОЛЖНО (SHALL) рассматривать лишь ограниченное число записей `data.limits`,
чтобы неожиданно большой ответ не мог раздуть данные, записываемые на диск.

#### Scenario: Слишком длинный массив лимитов усекается
- **WHEN** ответ несёт намного больше записей лимитов, чем сообщает любой известный тариф
- **THEN** разбор проходит успешно, окна квоты по-прежнему определяются из ведущих записей,
  а сохраняемые данные остаются ограниченными

### Requirement: Наличие недельного окна переживает круговой прогон через кэш
Расширение ДОЛЖНО (SHALL) сохранять наличие недельного окна явным значением и восстанавливать
его без изменений при выдаче данных квоты из кэша, для каждого провайдера.

Расширение также принимает запись кэша, записанную предыдущей версией схемы, выводя наличие
недельного окна так, как это делала та версия, и всегда пишет текущую версию. Это не даёт
двум версиям расширения, работающим с одним файлом кэша, обесценивать записи друг друга
и опрашивать API на каждом тике, пока не будут перезапущены все окна.

#### Scenario: Тариф без недельного окна остаётся без него
- **WHEN** данные квоты без недельного окна записаны в кэш и прочитаны обратно
- **THEN** восстановленные данные по-прежнему сообщают об отсутствии недельного окна

#### Scenario: Тариф с недельным окном его сохраняет
- **WHEN** данные квоты с недельным окном записаны в кэш и прочитаны обратно
- **THEN** восстановленные данные по-прежнему сообщают о наличии недельного окна

#### Scenario: Запись кэша предыдущей версии по-прежнему читается
- **WHEN** файл кэша содержит запись, сделанную предыдущей версией схемы
- **THEN** она принимается на чтение, а ближайшая запись выполняется в текущей версии

#### Scenario: Испорченная запись кэша по-прежнему отвергается
- **WHEN** запись кэша несёт утилизацию вне диапазона или неизвестный статус лимита
- **THEN** запись отвергается независимо от версии схемы

### Requirement: Величины кредитов и уровень тарифа показываются только при наличии
Расширение ДОЛЖНО (SHALL) показывать абсолютные величины рядом с тем окном, к которому они
относятся, когда эти величины есть, и полностью убирать этот показ, когда их нет, — а это
все провайдеры, кроме z.ai, и все токенные тарифы z.ai. Уровень тарифа показывается, когда
он есть, в экранированном виде, и не показывается иначе.

#### Scenario: Кредитный тариф показывает величины и уровень
- **WHEN** дашборд отрисовывает данные квоты с величинами кредитов и уровнем тарифа
- **THEN** величины появляются рядом со своим окном, а уровень показан

#### Scenario: Anthropic не показывает ни того, ни другого
- **WHEN** дашборд отрисовывает данные квоты Anthropic
- **THEN** ни блок величин, ни значок уровня не показываются

#### Scenario: Токенный тариф не показывает величин
- **WHEN** дашборд отрисовывает данные квоты z.ai, сообщающие только проценты
- **THEN** блок величин не показывается, а показ процентов не меняется

### Requirement: Разбор заголовков ограничений Anthropic не меняется
Расширение ДОЛЖНО (SHALL) выводить данные об ограничениях Anthropic из заголовков ответа,
когда статус ответа не 401, не 403 и не 5xx и ответ несёт хотя бы один из заголовков
`anthropic-ratelimit-unified-5h-utilization`, `anthropic-ratelimit-unified-7d-utilization`,
`anthropic-ratelimit-unified-5h-reset`, `anthropic-ratelimit-unified-7d-reset`,
`anthropic-ratelimit-unified-5h-status` (далее — единые заголовки ограничений), трактуя времена сброса как секунды эпохи Unix, и не заполнять для ответов
Anthropic специфичные для z.ai поля модели тарификации, уровня тарифа и величин кредитов.
Иной ответ данных об ограничениях не даёт.

#### Scenario: Заголовки Anthropic разбираются без изменений
- **WHEN** ответ Anthropic несёт единые заголовки пятичасовой и семидневной утилизации
  и сброса
- **THEN** сообщённые утилизации и горизонты сброса выводятся из этих заголовков, а времена
  сброса читаются как секунды эпохи Unix

#### Scenario: Тариф без семидневного заголовка не сообщает недельного окна
- **WHEN** ответ Anthropic не несёт семидневного заголовка сброса
- **THEN** недельное окно считается отсутствующим

#### Scenario: Специфичные для z.ai поля остаются пустыми
- **WHEN** данные об ограничениях получены из ответа Anthropic
- **THEN** ни модель тарификации, ни уровень тарифа, ни величины кредитов не отдаются

#### Scenario: Исчерпанный лимит с кодом 429 по-прежнему даёт denied
- **WHEN** Anthropic отвечает статусом 429 и заголовком пятичасового статуса `denied`
- **THEN** статус лимита сообщается как `denied`, а не как неудачный запрос

### Requirement: Истёкший токен Anthropic не отправляется в API
Расширение ДОЛЖНО (SHALL) не отправлять запрос ограничений Anthropic, если срок действия
OAuth-токена, записанный рядом с ним, истёк или истекает в ближайшие 60 секунд, и в этом
случае не ставить опрос на паузу, не показывать состояние отвергнутых учётных данных
и сообщать, что токен истёк и его обновит любой запрос в Claude Code. Срок, не являющийся
правдоподобной отметкой времени в миллисекундах, считается отсутствующим.

#### Scenario: Истёкший токен не порождает запроса
- **WHEN** срок действия токена в учётных данных уже прошёл
- **THEN** запрос к API не отправляется, и в кэш ничего не пишется

#### Scenario: Токен, истекающий в пределах запаса, не отправляется
- **WHEN** срок действия токена истекает через 30 секунд
- **THEN** запрос к API не отправляется

#### Scenario: Токен с запасом отправляется
- **WHEN** срок действия токена истекает через 120 секунд
- **THEN** запрос к API отправляется

#### Scenario: Истёкший токен не выдаётся за отвергнутый вход
- **WHEN** опрос пропущен из-за истёкшего токена
- **THEN** показываются закэшированные, протухшие данные или режим затрат с пометкой
  об истёкшем токене в подсказке, а не состояние отвергнутых учётных данных

#### Scenario: Истёкший токен без данных не советует обновить
- **WHEN** опрос пропущен из-за истёкшего токена, кэша нет, и локальных затрат нет
- **THEN** метка сообщает, что вход истёк, без цвета ошибки, а не предлагает обновить данные

#### Scenario: Обновлённый токен подхватывается без ожидания паузы
- **WHEN** опрос был пропущен из-за истёкшего токена, после чего Claude Code записал
  новый токен
- **THEN** ближайшее обновление, которое по правилам свежести кэша обращается к API,
  отправляет запрос

#### Scenario: Неправдоподобный срок не останавливает опрос
- **WHEN** срок действия в учётных данных отсутствует, не является числом, меньше `1e12`
  или отстоит от текущего момента больше чем на год вперёд
- **THEN** запрос к API отправляется

#### Scenario: На macOS истёкший файл не заслоняет Keychain
- **WHEN** на macOS при пути учётных данных по умолчанию токен в файле истёк, а в Keychain
  лежит токен с более поздним сроком
- **THEN** запрос отправляется с токеном из Keychain

#### Scenario: Keychain не читается без опроса
- **WHEN** на macOS токен в файле истёк, а обновление не обращается к API (кэш свежий,
  пауза или определение провайдера)
- **THEN** Keychain не читается

### Requirement: Отказ учётных данных Anthropic распознаётся по статусу ответа
Расширение ДОЛЖНО (SHALL) считать ответ Anthropic со статусом 401 или 403 отказом класса
«аутентификация», даже если ответ несёт заголовки ограничений, и не выводить из такого
ответа данных об ограничениях.

#### Scenario: Отвергнутый токен даёт отказ аутентификации
- **WHEN** Anthropic отвечает статусом 401 без заголовков ограничений на неистёкший токен
- **THEN** запрос завершается отказом класса «аутентификация», и в кэш ничего не пишется

#### Scenario: Запрет доступа даёт отказ аутентификации
- **WHEN** Anthropic отвечает статусом 403
- **THEN** запрос завершается отказом класса «аутентификация»

#### Scenario: Заголовки не перевешивают отказ
- **WHEN** Anthropic отвечает статусом 401 или 403, и ответ несёт заголовки ограничений
- **THEN** запрос завершается отказом класса «аутентификация», а заголовки не разбираются

### Requirement: Сбой сервера Anthropic остаётся повторяемым
Расширение ДОЛЖНО (SHALL) считать ответ Anthropic со статусом 5xx неудачным запросом
повторяемого класса: без записи в кэш, без паузы опроса на время жизни кэша и без указания
на учётные данные.

#### Scenario: Ошибка сервера не ставит опрос на паузу на время жизни кэша
- **WHEN** Anthropic отвечает статусом 500 или 529
- **THEN** запрос завершается неудачей повторяемого класса, в кэш ничего не пишется,
  и учётные данные не называются

### Requirement: Ответ Anthropic без заголовков ограничений считается дрейфом формата
Расширение ДОЛЖНО (SHALL) считать ответ Anthropic, который не является отказом
аутентификации или сбоем сервера и не несёт ни одного из единых заголовков ограничений,
неудачным запросом класса «формат», чтобы такой ответ проявлялся как протухшие или
закэшированные данные, а не как нулевой расход.

#### Scenario: Успешный ответ без заголовков не даёт нулевого расхода
- **WHEN** Anthropic отвечает статусом 200 без единых заголовков ограничений
- **THEN** запрос завершается неудачей класса «формат», и «0 % использовано» не кэшируется

#### Scenario: Клиентская ошибка без заголовков тоже считается дрейфом формата
- **WHEN** Anthropic отвечает статусом 400 или 404 без единых заголовков ограничений
- **THEN** запрос завершается неудачей класса «формат»

#### Scenario: 429 без заголовков не повторяется каждый тик
- **WHEN** Anthropic отвечает статусом 429 без единых заголовков ограничений
- **THEN** запрос завершается неудачей класса «формат»

### Requirement: Неудача класса «формат» не обвиняет учётные данные
Расширение ДОЛЖНО (SHALL) после неудачи класса «формат» у любого провайдера не показывать
ни состояние отвергнутых учётных данных, ни состояние невыполненного входа.

#### Scenario: Дрейф формата с кэшем не выдаётся за проблему с ключом
- **WHEN** запрос квоты завершился неудачей класса «формат», и кэш есть
- **THEN** показываются закэшированные или протухшие данные, учётные данные не называются

#### Scenario: Дрейф формата без кэша не выдаётся за невыполненный вход
- **WHEN** запрос квоты завершился неудачей класса «формат», и кэша нет
- **THEN** показывается режим затрат или отсутствие данных, а не «вход не выполнен»

### Requirement: Ручное обновление обходит паузу опроса
Расширение ДОЛЖНО (SHALL) при ручном обновлении запрашивать квоту, даже если автоматический
опрос поставлен на паузу или отложен после повторяемой неудачи. Если межоконную блокировку
опроса держит другое окно, это окно запроса не отправляет, показывает текущее состояние
с учётом активной паузы, а результат соседнего окна подхватывает ближайшим обновлением.

#### Scenario: После повторного входа ручное обновление опрашивает сразу
- **WHEN** опрос на паузе после отказа аутентификации, и пользователь запускает ручное
  обновление
- **THEN** запрос провайдеру отправляется, и при успехе пауза снимается

#### Scenario: Ручное обновление при чужой блокировке не мигает
- **WHEN** опрос на паузе после отказа аутентификации, блокировку держит другое окно,
  и пользователь запускает ручное обновление
- **THEN** запрос не отправляется, и состояние отвергнутых учётных данных сохраняется

#### Scenario: Неудачное ручное обновление паузу не снимает
- **WHEN** ручное обновление во время паузы снова завершается отказом аутентификации
- **THEN** пауза остаётся в силе для автоматических обновлений

### Requirement: Пауза снимается свежими данными соседнего окна
Расширение ДОЛЖНО (SHALL) снимать паузу опроса, задержку повтора и пометку причины неудачи,
когда в общем кэше появилась запись того же провайдера, записанная позже момента неудачи,
и не показывать пометку причины, относящуюся к другому провайдеру.

#### Scenario: Успех другого окна снимает отказ
- **WHEN** окно запомнило отказ аутентификации, а другое окно затем успешно опросило того же
  провайдера и записало кэш
- **THEN** первое окно показывает данные из кэша без состояния отвергнутых учётных данных

#### Scenario: Более старый кэш отказ не снимает
- **WHEN** запись кэша того же провайдера сделана раньше момента отказа
- **THEN** пауза и состояние отвергнутых учётных данных сохраняются

#### Scenario: Смена провайдера убирает чужую пометку
- **WHEN** пометка об истёкшем токене Anthropic записана, после чего активным провайдером
  стал z.ai
- **THEN** пометка об истёкшем токене не показывается

### Requirement: Подсказки о входе верны для провайдера и причины
Расширение ДОЛЖНО (SHALL) называть способ исправления, подходящий провайдеру и причине:
для отвергнутого входа Anthropic (401 или статус неизвестен) — `claude auth login` и затем
ручное обновление под тем названием команды, которое показывает палитра на языке интерфейса; для запрета доступа Anthropic (403) — нейтральное
сообщение с кодом статуса без совета войти заново; для z.ai — проверку
`ANTHROPIC_AUTH_TOKEN` (или `ANTHROPIC_API_KEY`) в `~/.claude/settings.json`; при отсутствии
учётных данных — `claude auth login` для Anthropic, настройку `ANTHROPIC_AUTH_TOKEN` для z.ai,
а когда провайдер не определён — оба пути. Команда `claude login`, которой в Claude Code
нет, не предлагается нигде.

#### Scenario: Anthropic при 401 советует войти заново
- **WHEN** учётные данные Anthropic отвергнуты со статусом 401
- **THEN** подсказка предлагает выполнить `claude auth login`, затем ручное обновление,
  и не упоминает `ANTHROPIC_AUTH_TOKEN`

#### Scenario: Anthropic при 403 не советует входить
- **WHEN** Anthropic отказал в доступе со статусом 403
- **THEN** подсказка называет код 403 и не предлагает `claude auth login`

#### Scenario: z.ai советует проверить ключ
- **WHEN** учётные данные отвергнуты, а провайдер — z.ai
- **THEN** подсказка предлагает проверить `ANTHROPIC_AUTH_TOKEN` в `~/.claude/settings.json`

#### Scenario: Невыполненный вход называет рабочую команду для провайдера
- **WHEN** расширение показывает состояние невыполненного входа для Anthropic
- **THEN** подсказка содержит `claude auth login`

#### Scenario: Невыполненный вход z.ai не советует claude auth login
- **WHEN** расширение показывает состояние невыполненного входа для z.ai
- **THEN** подсказка называет `ANTHROPIC_AUTH_TOKEN` и не содержит `claude auth login`

#### Scenario: Неопределённый провайдер называет оба пути входа
- **WHEN** расширение показывает состояние невыполненного входа, а провайдер не определён
- **THEN** подсказка содержит и `claude auth login`, и `ANTHROPIC_AUTH_TOKEN`

#### Scenario: Отказ без известного статуса трактуется как отвергнутый вход
- **WHEN** состояние отвергнутых учётных данных Anthropic показывается без кода статуса
- **THEN** подсказка та же, что при статусе 401

#### Scenario: Название команды обновления совпадает с палитрой
- **WHEN** подсказка об отвергнутом входе показывается на английском, русском, японском
  или китайском
- **THEN** она называет команду обновления так же, как её показывает палитра команд
  на этом языке

### Requirement: Утилизация показывается только при живых данных об ограничениях
Расширение ДОЛЖНО (SHALL) использовать утилизацию и время сброса — в полосах и графике
дашборда, в прогнозе и в уведомлениях о порогах — только когда данные об ограничениях
получены из API или кэша, не считать их отсутствие сбросом окна и не выдавать нулевую утилизацию снимка без таких данных
за протухшие данные.

#### Scenario: Отвергнутый вход не рисует утилизацию
- **WHEN** дашборд получает данные в состоянии отвергнутых учётных данных
- **THEN** полосы утилизации и график прогноза не показываются, а строка состояния называет
  отвергнутые учётные данные

#### Scenario: Отвергнутый вход не шлёт уведомлений о порогах
- **WHEN** данные в состоянии отвергнутых учётных данных несут утилизацию из старого кэша
  выше порога
- **THEN** уведомление о пороге не показывается, и прогноз не опирается на эту утилизацию

#### Scenario: Переход к живым данным не выглядит как сброс окна
- **WHEN** после состояния без живых данных об ограничениях снова приходят живые данные
  о том же окне
- **THEN** ключи уже показанных уведомлений о порогах не сбрасываются, и повторного
  уведомления о том же пороге нет

#### Scenario: Истёкший токен назван на дашборде
- **WHEN** дашборд получает данные с пометкой истёкшего токена
- **THEN** строка состояния называет истёкший токен

#### Scenario: Снимок без живых данных не показывает ноль как протухшие данные
- **WHEN** при запуске загружается снимок состояния без данных об ограничениях
- **THEN** до первого обновления показывается состояние снимка, а не «0 %» с пометкой возраста

### Requirement: Сообщение об отказе Anthropic не раскрывает токен
Расширение ДОЛЖНО (SHALL) формировать сообщение о неудачном запросе Anthropic без OAuth-токена
и без тела ответа, называя только код статуса.

#### Scenario: Токен не попадает в сообщение
- **WHEN** запрос Anthropic завершается отказом аутентификации
- **THEN** сообщение неудачи содержит код статуса и не содержит токена
