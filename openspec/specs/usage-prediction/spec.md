# usage-prediction Specification

## Purpose
Скорость прожигания квоты и прогноз её исчерпания в единицах провайдера: кредиты z.ai
по официальной формуле с множителями по моделям и скидкой вне пика, доллары — по действующему расчёту стоимости расширения (прайс-лист настроек ценообразования; сама долларовая формула в этой спеке не переопределяется); прогноз сверяется с реальной квотой из кэша.

## Requirements

### Requirement: Скорость прожигания считается одним движком в двух единицах
Расширение ДОЛЖНО (SHALL) вычислять скорость прожигания по локальным записям JSONL скользящего окна одним движком, который отдаёт результат одновременно в кредитах z.ai и в долларах США. Выбор единицы отображения на расчёт не влияет: обе величины всегда доступны потребителям. В расчёт входят и ходы субагентов из подкаталогов subagents — без них скорость систематически занижена. Скользящее окно — 30 минут: в расчёт входят ходы с отметкой времени не старше (текущий момент − 30 минут); скорость равна сумме величин ходов окна, делённой на часы от отметки первого хода окна до текущего момента; меньше двух ходов в окне — скорость 0 в обеих единицах. Нижний предел знаменателя не вводится: всплеск из нескольких самых свежих ходов даёт завышенную оценку скорости, и прогноз по ней консервативен — предупреждает раньше, а не позже. При нулевом интервале — первый ход окна в текущей миллисекунде — скорость считается нулевой. Записи дедуплицируются по идентификатору запроса (requestId, иначе id сообщения) — сессия и её субагенты не задваивают один ход. Запись без обоих идентификаторов не дедуплицируется.

#### Scenario: Одни записи дают обе величины
- **WHEN** движок получает записи ходов за скользящее окно
- **THEN** он отдаёт скорость в кредитах в час и в долларах в час за один расчёт

#### Scenario: Единица отображения не меняет расчёт
- **WHEN** первичная единица переключается между кредитами и долларами
- **THEN** пересчитываются только показания, а не сам движок скорости

#### Scenario: Ходы субагентов входят в скорость
- **WHEN** в окне есть ходы главной сессии и ходы её субагентов на GLM-моделях
- **THEN** скорость учитывает и те, и другие записи

#### Scenario: Меньше двух ходов дают нулевую скорость
- **WHEN** в 30-минутном окне один ход
- **THEN** скорость прожигания — 0 в обеих единицах, прогноз по скорости не строится

### Requirement: Кредиты z.ai считаются по официальной формуле с множителями модели
Расширение ДОЛЖНО (SHALL) считать кредиты z.ai каждого хода как `(input × M_in + cache_read × M_cache + output × M_out) / 10000`, беря множители по модели хода: GLM-5.3 — 6.9 / 1.7 / 24, GLM-5.3-Flash — 2.3 / 0.56 / 8; слагаемого `cache_creation_input_tokens` в формуле нет, и к input эти токены не прибавляются: тариф z.ai не выставляет записи кэша отдельным слагаемым. Отсутствующее или нечисловое значение поля записи считается нулём; слагаемые независимы — cache_read в input не входит. Множители и делитель взяты из справочника тарифов z.ai (design D7); при изменении тарифа обновляются вместе с кодом.

#### Scenario: Ход GLM-5.3 считается по базовым множителям
- **WHEN** ход модели GLM-5.3 несёт input 1000, cache_read 1000, output 100
- **THEN** кредиты хода составляют 1.1

#### Scenario: Ход Flash считается по множителям Flash
- **WHEN** тот же объём токенов несёт ход модели GLM-5.3-Flash
- **THEN** кредиты хода составляют 0.366 по множителям 2.3 / 0.56 / 8 — они заданы
  независимо, приблизительно треть базовых

#### Scenario: Cache creation не прибавляет кредитов
- **WHEN** два хода GLM-5.3 совпадают по input, cache_read и output, но различаются
  по cache_creation
- **THEN** кредиты обоих ходов равны

### Requirement: Кредиты начисляются только ходам GLM-моделей
Расширение ДОЛЖНО (SHALL) включать в кредитные агрегаты только ходы GLM-моделей: ходы claude-* и неизвестных моделей не начисляют кредитов. Запись JSONL не несёт провайдера, а история может быть смешанной — кредитная модель z.ai не приписывает Anthropic-токены кредитному тарифу. GLM-моделью считается имя, содержащее `glm` или `flash` — flash-тиры тарифицируются как тарифные классы того же GLM-семейства, имя с `flash` и без `glm` тоже тарифицируется множителями Flash — отдельного исключения для него нет. Множители: имя содержит `flash` — множители Flash, иначе (имя содержит `glm`) — базовые множители GLM-5.3, включая будущие версии семейства (glm-4.x, glm-5.4); сопоставление — подстрокой в нижнем регистре.

#### Scenario: Ход модели claude не прибавляет кредитов
- **WHEN** в окне расчёта ход glm-5.3 (кредиты 1.1) и ход claude-opus-5-5
- **THEN** кредитная сумма окна — 1.1: ход claude-модели в кредиты не входит

#### Scenario: Будущая GLM-версия считается базовыми множителями
- **WHEN** ход модели `glm-5.4` несёт тот же объём токенов, что ход `glm-5.3`
- **THEN** кредиты хода считаются по базовым множителям 6.9 / 1.7 / 24

#### Scenario: Регистр имени модели не влияет на кредиты
- **WHEN** имя модели хода — `GLM-5.3` в верхнем регистре
- **THEN** ход начисляет кредиты по базовым множителям

### Requirement: Вне пика кредиты делятся пополам
Расширение ДОЛЖНО (SHALL) применять к кредиту каждого хода коэффициент 0.5, когда
отметка времени хода попадает вне пик-часов z.ai, и базовый коэффициент — внутри
пика, так что сессия, пересекающая границу пика, оценивается почасово по обеим
ставкам. Границы пик-часов заданы спекой `zai-peak-hours` (будние дни 06:00–10:00 UTC).

#### Scenario: Одинаковый ход в пике и вне пика стоит вдвое по-разному
- **WHEN** два одинаковых хода GLM-5.3 совершены в будний день в 07:00 UTC и в 12:00 UTC
- **THEN** кредит второго хода равен половине кредита первого

#### Scenario: Выходной весь день вне пика
- **WHEN** ход совершён в субботу 07:00 UTC
- **THEN** к его кредиту применён коэффициент 0.5

### Requirement: Прогноз исчерпания сверяется с реальной квотой
Расширение ДОЛЖНО (SHALL) при живых данных квоты z.ai с абсолютными величинами считать прогноз исчерпания 5-часового окна из остатка окна credits5h и скорости прожигания в кредитах, ограничивая горизонт временем сброса (reset5hAt); если окно не исчерпается до сброса — сообщать именно это. Контракт полей квоты: `used` — израсходовано за окно, `total` — лимит окна, `remaining` — остаток как сообщено (провайдер округляет дробные кредиты, поэтому остаток из used и total не пересчитывается); при отсутствии `remaining` остаток считается как `total − used`. При нулевой скорости (в окне нет ходов) прогноз исчерпания не строится. Без абсолютных величин прогноз оценивается из утилизации и расхода за окно по явной формуле: полная ёмкость 5-часового окна квоты = расход за это же 5-часовое окно / утилизация (окно квоты, а не 30-минутное окно скорости) Расход за 5-часовое окно — локальный счёт записей лога за текущее окно квоты: для z-ai кредиты по формуле этой спеки, для остальных провайдеров — доллары по прайс-листу. При малых утилизациях вычисленное время упирается в горизонт сброса — прогноз не превышает время сброса.; остаток = ёмкость × (1 − утилизация); время исчерпания = остаток / скорость, причём расход и скорость берутся в одной единице (кредиты для z-ai, доллары для остальных); горизонт ограничен временем сброса. Утилизация здесь — доля 0–1: при 0 (расхода нет) формула не строится, при утилизации ≥ 1 прогноз не строится — констатируется достигнутый лимит окна.

#### Scenario: Запас перекрывает скорость до сброса
- **WHEN** израсходовано 5000 из 28000 кредитов, скорость 4000 кредитов в час,
  до сброса 2 часа
- **THEN** прогноз сообщает, что окно не исчерпается до сброса

#### Scenario: Скорость ведёт к исчерпанию до сброса
- **WHEN** остаётся 1000 кредитов, скорость 4000 кредитов в час, до сброса 2 часа
- **THEN** прогноз сообщает исчерпание примерно через 15 минут

#### Scenario: Токенный тариф оценивается по утилизации
- **WHEN** квота z.ai не сообщает абсолютных величин, а только проценты
- **THEN** прогноз исчерпания строится по формуле утилизации: ёмкость = расход за
  окно / утилизация, время до исчерпания = остаток / скорость

#### Scenario: Нулевая скорость не даёт прогноза
- **WHEN** в окне скорости меньше двух ходов (нет ходов или ровно один), а квота z.ai живая и с величинами
- **THEN** прогноз исчерпания не показывается

### Requirement: Прогноз не опирается на неживые данные квоты
Расширение ДОЛЖНО (SHALL) использовать величины кредитов из кэша в прогнозе только
при живых данных об ограничениях и не строить прогноз исчерпания по протухшим
величинам — в согласии с требованием «Утилизация показывается только при живых
данных об ограничениях» спеки `zai-quota-parsing` (openspec/specs/zai-quota-parsing/spec.md).

#### Scenario: Протухший кэш не даёт прогноза исчерпания
- **WHEN** данные квоты с величинами кредитов показаны как протухшие
- **THEN** прогноз не утверждает исчерпание из этих величин и показывается без него
